# ADR 0088 — Clients: tags

Status: accepted (2026-10); extends [ADR 0056](0056-clients-edit-replaces-contact-composition.md) (the edit replaces
the whole record) and [ADR 0049](0049-conventions-for-new-backend-slices.md) §2 (a many-to-many between aggregates is
a child of the owner that keeps the other's id)

## Context

A person (`Client`) had no link to a tag. Only `Service` had one, through the `ServiceTags` join table, which belongs to
the older generation (ARCHITECTURE §10): an EF skip navigation from `Service` to `Tag`. The product wants to tag
people, backend first, with the frontend in a separate change. It settled the contract up front: create and update
take `tagIds`, a `null` on the `PUT` clears them, every read and mutation response carries the tags, deleting a tag
that people use is blocked, and the list gets no tag filter yet.

## Decision

**A `ClientTag` child that keeps the tag's id.** `Client` owns a collection of `ClientTag` (`ClientId`, `TagId`),
a `TenantOwnedEntity` created only by the root (`ClientTag.Create` is `internal`). The domain never loads a `Tag`.
`ServiceTags` is not a precedent and is not migrated: it predates ADR 0049 and links two roots by navigation.

**Persistence.** Table `services.ClientTags`, key generated by the factory (`ValueGeneratedNever`, as for the contacts
in ADR 0056). Both foreign keys are composite with the tenant: `(TenantId, ClientId)` to `Clients` with cascade, and
`(TenantId, TagId)` to the alternate key `(TenantId, Id)` of `Tags` with restrict, so the database refuses a link to
another tenant's tag or person. A unique index on `(TenantId, ClientId, TagId)` filtered by `"DeletedAt" IS NULL`
refuses two live links to the same tag and lets a tag removed earlier be linked again. An index on
`(TenantId, TagId)` serves the usage count. Migration `AddClientTags` only adds; its `Down` drops the table.

**Input.** `CreateClientCommand` and `UpdateClientCommand` gain `tagIds: Guid[] | null`. The mapping turns `null` into
an empty list, so on the `PUT`, as with guardians and reference contacts (ADR 0056), a missing or `null` `tagIds` and
`[]` all leave the person without tags. There is no endpoint that adds or removes one tag.

**Rules.** `Client.MaxTags = 20`: more is `Client.TooManyTags`, a repeated id is `Client.DuplicateTag`; both are domain
errors, validated before anything is assigned, so a refused `Update` leaves the aggregate untouched. The validators
repeat both rules with the same codes, attached to `TagIds`, and add `Client.TagIdRequired` for an empty id; the item
rules do not run when the list is over the limit. On `Update`, a tag that stays keeps its `ClientTag` row (same id, no
audit churn), a tag that leaves is soft-deleted and a new one gets a new row. The contacts are recreated instead; a
link has nothing to edit.

**Unknown tag.** After the domain call and before staging, the create and update handlers read the tags with
`ITagRepository.GetByIdsAsync`. A missing one (unknown, soft-deleted or another tenant's, all hidden by the query
filters) is `400` with code `Tag.NotFound` on the field `TagIds`: it is a form error, not the resource of the URL.
Services answer `404` in the same case; the difference is intentional.

**Output.** `ClientResponse` (GET by id, create, update, deactivate, reactivate) and `ClientListItemResponse` carry
`tags: [{ id, name, color }]`, ordered by name then id. `TagSummary`, which services already returned, moves to
`Application/Tags` with a `FromTag` factory; its schema id is unchanged. The handlers pass the tag ids straight to
`GetByIdsAsync`; the list reads the tags of the whole page with one call, never one per row. `TagRepository.GetByIdsAsync`
returns an empty list without a query when it gets no ids, so nothing is read when nobody has tags.

**Deleting a tag in use.** `DeleteTag` counts services and people (`IClientRepository.CountByTagIdAsync`, through the
filters; an inactive person counts, a deleted one does not) and answers `409 Tag.InUse` when either is above zero. The
code does not change; the pt-BR message names only the non-zero parts ("2 serviço(s)", "3 pessoa(s)", or both).

**No tag filter on the list.** `ListClientsQuery` gets no `tagId`; it is a later decision.

## Consequences

- Wire: `services-api.d.ts` is regenerated in this change with `tagIds: null | string[]` on both commands and `tags` on
  both client responses; nothing in services or tags changes.
- `tagIds` is **required** in the generated schema, as `guardians` and `referenceContacts` already are: ASP.NET's
  OpenAPI marks every positional record parameter without a default as required. Making the parameter optional
  with a default was considered and turned down by product choice.
- Stopgap so the required frontend check stays green: `clientsRepository.ts` sends `tagIds: []` on create and update
  until the frontend change replaces it with the form's tags. It is the only frontend line this change touches.
- Until the frontend change ships, any edit made through the current person form **clears that person's tags**, since
  the form sends an empty `tagIds`. No screen sets tags before then, so nothing is lost today, but the effect is real.
- ARCHITECTURE §10 points to `ClientTag` and `ClientTagConfiguration` as the example of a many-to-many between
  aggregates kept by id.
- Reading a client loads three collections (up to 10 guardians, 10 reference contacts and 20 tags), so
  `ClientRepository` loads them with a split query instead of one join that multiplies their rows.
- Accepted limit, as for services: a tag deleted between a client's tag read and its save leaves a live link to a
  soft-deleted tag, since the soft delete is an `UPDATE` the restrict FK does not see. The tag disappears from that
  person's own responses, but the list maps each link straight to its tag and answers `500` for the whole page
  until an edit of that person removes the link. No row lock guards this window and the list does not skip a
  missing tag: both were turned down for a race this unlikely.
- Accepted limit of the split query on the list: the page and each collection are separate statements, so a person
  inserted or renamed ahead of the page between them shifts it, and a person on the page can come back with empty
  tags or contacts. The list is read without tracking and never saved, so the next load corrects it. A single
  statement brings back the joined rows and a `REPEATABLE READ` transaction was turned down as a new mechanism for
  an unlikely race.

Verified by hand on a disposable PostgreSQL 18 started from `infra/postgres/init`: the migration chain applied from
zero, then `AddClientTags` Down and Up again. As `services_app`: a link to another tenant's tag and to another tenant's
person each failed on its composite FK; a second live link to the same tag failed on the filtered unique index and
was accepted after the first was soft-deleted; deleting a linked tag failed on restrict; deleting the person cascaded.
Against the real services on private ports, 22 API checks passed, among them create, read, list, a `PUT` that keeps the
row of a tag that stays, a `PUT` without `tagIds` that clears, `400 Tag.NotFound` for an unknown and for another
tenant's tag, and `409 Tag.InUse` for a tag used by an inactive person.

## Considered and rejected

- **Copying `ServiceTags`, a skip navigation from `Client` to `Tag`.** It loads another root into the aggregate and
  is the older generation ADR 0049 replaced.
- **`null` on the `PUT` keeps the current tags.** The `PUT` replaces the whole record (ADR 0056); a field that means
  "unchanged" when absent would be the only one of its kind.
- **`404` for an unknown tag, as services do.** The URL's resource exists; the problem is a value in the form.
- **Removing the links when a tag is deleted.** The product chose to block, as for services.
- **Deactivate and reactivate without tags.** Tried in this change and reverted: both keep returning the whole
  `ClientResponse`.
